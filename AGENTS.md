# AGENTS.md

Инструкции для Claude Code, Codex и OpenCode при работе с **MultiProjectStore (MPS)**.

MultiProjectStore — харнес-агностичный форк ProjectStore: единый движок проекта (решения,
спеки, эпики, истории, канбан — как markdown в git) с одним CLI `mps` и одним набором ролей
агентов, которые одинаково доступны из любого харнеса. Никаких hooks, statusLine и
slash-команд как обязательного интерфейса.

## Обязательная загрузка контекста

До анализа задачи, плана, правок или запуска проверок:

1. Прочитать этот `AGENTS.md` полностью.
2. Выполнить `mps brief` — пакет ориентации по привязанному vault (где что лежит, что в
   работе, в каком порядке читать). Это замена SessionStart-хука исходника.
3. Прочитать `docs/decisions/README.md` и связанные ADR — если задача затрагивает
   архитектуру форка, CLI, роли, layouts, шаблоны или рабочую механику.
4. `mps status` — какой vault привязан и в каком состоянии роли по харнесам.

## Что делает MPS

- **Vault** — каталог с артефактами как markdown в git: `adr/`, `specs/`,
  `epics/<id>/stories/`, `research/`, `concepts/`, `meetings/`, `ops/`, `diagrams/`
  (layout `engineering`).
- **Проверенный цикл**: задача → артефакт (ADR/спека/эпик/история) → critic → бэклог →
  planner → reviewer → done. Каждая проверка — отдельный проход со свежим контекстом.
- **Deterministic doctor**: `mps doctor` проверяет консистентность без AI.

## Единый CLI (вместо slash-команд)

| Команда | Что делает |
|---------|------------|
| `mps bind <vault>` | привязать vault и развернуть layout (`--layout`, `--lang`, `--force`) |
| `mps scaffold` | до-создать папки layout и README-индексы |
| `mps brief` | пакет ориентации на старте работы |
| `mps draft <kind> "<title>" [--write]` | черновик артефакта; `--write` создаёт и пересобирает представления |
| `mps story plan\|close <path> [--write]` | гейты жизненного цикла истории |
| `mps kanban` / `graph` / `codemap` | пересоздать одно производное представление |
| `mps reconcile [--write]` | пересобрать все представления и индексы |
| `mps doctor [--install\|--vault] [--fix]` | диагностика консистентности |
| `mps diff-refs` | изменённые файлы как доказательства для `code_refs` |
| `mps agents …` | роли: `list`/`show`/`install`/`uninstall`/`register`/`model` |
| `mps harnesses` | какие харнесы поддержаны, куда кладутся роли, как их звать |
| `mps prompt [name]` / `mps skill [name]` | процедуры цикла и скиллы |
| `mps sessions [--touch] [--claim/--release]` | реестр активных сессий и заявок на истории |
| `mps commit -m "<что>"` | коммит с трейлерами харнеса/сессии/истории |
| `mps merge <ref>` | слияние с пересборкой производных представлений |
| `mps log [--story\|--harness]` | история по трейлерам |
| `mps watch` | держать сессию живой и видеть события других устройств |
| `mps lease <path…>` | объявить файлы, которые правишь сейчас |
| `mps storage` | на чём лежит vault и насколько может отставать присутствие |
| `mps tokens` | во что обошёлся цикл — только по транскриптам Claude Code |
| `mps status`, `mps help` | сводка и справка |

Все записи на диск делает диспетчер `bin/mps`; скрипты в `scripts/` — чистое вычисление,
печатающее JSON. Не писать производные представления руками: они пересоздаются.

## Роли агентов (одинаковые во всех харнесах)

Определение роли одно — `agents/<role>.md`; `mps agents install` рендерит его в формат
того харнеса, которым пользуется проект. Список — `mps harnesses`: Claude Code, Codex,
OpenCode, Kimi Code CLI, Qwen Code, ZCode (Z.ai), CodeBuddy Code, Tongyi Lingma, Cursor,
Windsurf, Cline, Copilot, Gemini CLI, Roo Code, DeepSeek Harness, Trae, iFlow. Это данные,
а не код:
харнес описывается JSON-файлом в `harnesses/`, свой можно добавить в `.mps/harnesses/`
(`docs/harnesses.md`). Где ролей как сущности нет — `mps agents show <role>` даёт готовый
промпт для отдельного запуска.

- **Каждая роль работает в свежем контексте, отдельном от автора.** Ревью собственной
  работы в собственном контексте отменяет весь смысл роли.
- `mps-critic` — после написания/правки артефакта или проектного предложения, до того как
  считать его финальным.
- `mps-planner` — до реализации эпика/истории: план с опорой на `code_refs` прошлых эпиков.
- `mps-reviewer` — после кода, до коммита/закрытия истории: закрывает ли дифф критерии приёмки.
- `mps-librarian`, `mps-archaeologist` — семантическая ревизия vault и раскопки решений в
  существующем коде.
- Роли read-only по контракту: правки запрещены картой инструментов там, где харнес её
  поддерживает, shell остаётся открытым — «не писать» держится на тексте роли. Они
  предлагают, а записи идут через approval-gated поток `mps`.
- Модель ролей: `mps agents model default <id>` действует на харнесы с опубликованными
  тирами (Claude Code); для остальных — `mps agents model harness:<name> <id>`. После смены
  модели переустановить: `mps agents install` (doctor покажет устаревшие файлы).
- Блок маршрутизации (`mps agents register`) — единственное место, откуда роли «зовутся»;
  править только вне маркеров.

## Параллельная работа в разных харнесах

Один проект могут одновременно вести несколько сессий (Claude Code, Codex, Cursor…).
Протокол — ADR-0006:

- **Коммитить через `mps commit -m "<что>" [--story <id>] [--all]`.** Он пересобирает
  производные представления, проверяет чужие заявки и записывает трейлеры
  `Mps-Harness` / `Mps-Session` / `Mps-Story`. Один коммит — одна история.
- **`mps log [--story|--harness|--session <v>]`** — та же история, прочитанная обратно.
  Коммит, сделанный мимо `mps commit`, трейлеров не получит: `mps log` покажет, сколько
  таких.
- **Открывая историю (`mps story plan --write`), сессия заявляет её**, закрывая — освобождает.
  Перед началом работы посмотреть `mps sessions`: если история уже за кем-то, это дубль.
- **Производные представления не сливать руками.** `mps doctor --fix` ставит
  `.gitattributes` и merge-драйвер; конфликт по `kanban.md`/`graph.md`/`code-map.md`/индексам
  разрешается пересборкой. Сливать ветки лучше через `mps merge <ref>` — тогда корректная
  доска попадает в сам merge-коммит.
- **Идентификатор сессии**: харнесу стоит экспортировать `MPS_SESSION_ID` (и `MPS_HARNESS`,
  если его нельзя определить по окружению) — иначе идентификатор выводится из терминала или
  из ppid и может «дробиться».

## Разные устройства и разные ОС (ADR-0007)

Vault может лежать в iCloud/Dropbox/на сетевой шаре, а сессии идти с macOS, Windows и Linux
одновременно. Правила:

- **В начале работы** — `mps sessions --touch` (или `mps watch` в фоне, если сессия длинная):
  без биения другие устройства вас не видят. `mps brief` и `mps status` показывают, кто ещё
  жив и что держит.
- **Перед правкой файлов, которые может трогать кто-то ещё** — `mps lease <path…>`.
  Отказ означает: файл прямо сейчас редактирует другая сессия (её устройство и харнес названы).
  `mps lease release` по завершении; `mps commit` сам откажется писать поверх чужой живой
  аренды.
- **Это advisory-координация, а не блокировка.** На облачном диске данные о другом устройстве
  могут отставать (команда сама скажет, на сколько). «Никто не работает» означает «ничего не
  синхронизировалось», а не «в мире никого нет».
- **Никогда не удалять чужое**: временные файлы других хостов, чужие presence/lease-записи,
  файлы без провенанса mps. Устаревшая аренда перехватывается штатно (`mps lease` запишет
  перехват), руками — нет.
- **Кросс-ОС гигиена**: `mps doctor` ловит имена, непереносимые на Windows, коллизии по
  регистру и отсутствие единой политики переводов строк; `--fix` прописывает `* text=auto`.
  Не создавать в vault имена с `<>:"|?*`, с завершающим пробелом/точкой и различающиеся только
  регистром.

## Как агент должен работать с vault

- **Перед архитектурным выбором** — прочитать `adr/README.md` и подходящий ADR, а не
  перерешать заново.
- **Feature-sized работа** — открыть epic/story до правки кода:
  `mps draft story <EPIC> "<title>"` (предпросмотр), затем `--write`.
- **После артефакта** — производные представления пересобираются автоматически при `--write`;
  вручную — `mps reconcile --write` (или `mps graph`, если графа ещё нет).
- **Проверка** — `mps doctor` перед завершением работы над vault.
- **Сессии** — `mps sessions --touch` в начале работы и `mps sessions` перед созданием новой
  темы/ADR, чтобы не дублировать работу параллельной сессии.

## Конфигурация

- Проект: `.mps/projectstore.json` (legacy — `.claude/projectstore.json`); машинно-локальный,
  в `.gitignore`.
- Vault: `<vault>/.projectstore.json` — политика (`spec_policy`, `lifecycle_gates`), едет с vault.
- Сгенерированные файлы ролей — наоборот, коммитятся: так вся команда получает одни роли.
- Переменные окружения: `MPS_PROJECT_DIR`, `MPS_HOME`, `MPS_SESSION_ID`.

## Архитектурные решения (ADR)

- Канонический источник решений MPS — `docs/decisions/`. Процесс — в
  `docs/decisions/README.md`, шаблон — `docs/decisions/0000-template.md`.
- Новый ADR — для долговременного решения с реальными альтернативами. Статус `proposed`,
  пока выбор не утверждён владельцем проекта.
- После принятия/замены обновить индекс ADR, связанную документацию и Memory-тему.

## Совместимость изменений

- **Код** (`.mjs`, `bin/mps`) — чистый node без внешних зависимостей; комментарии и строки
  на английском. Тесты: `npm test` (`node --test tests/*.test.mjs`).
- Не ломать харнес-агностичность: не вводить hooks, statusline или slash-команды как
  обязательный интерфейс; не добавлять запись в `.claude/` для не-Claude харнесов.
- Новая роль — файл в `agents/` с нейтральным frontmatter, а не правка адаптеров.
- Новый харнес — JSON в `harnesses/` (или `.mps/harnesses/` в проекте), а не ветка в
  рендерере. Уровень доверия — про доказательства: `verified` — формат из документации И
  проверен запуском; `documented` — взят из документации вендора (URL обязателен в поле
  `docs`); `inferred` — выведен по соглашению, и тогда в `notes` написано, что предположено.
- **CLI вендора и модели вендора — разные записи.** Moonshot, Zhipu, Alibaba, Tencent и
  DeepSeek поставляют и то и другое (`kimi`/`zcode`/`qwen`/`codebuddy`/`dsh` — инструменты,
  `moonshot`/`glm`/`dashscope`/`deepseek` — модели); MiniMax — только модели.
- Харнес без формата файлов ролей — нормальный случай (`roles.shape: "none"`, как у `dsh`):
  он всё равно получает блок маршрутизации, а роль вызывается через `mps agents show <role>`
  или через субагента, которого этот харнес умеет запускать.
  Роли ставятся для харнеса, а провайдер попадает в запись коммита трейлером `Mps-Provider`
  (`mps log --provider kimi`). Записи провайдеров — `harnesses/providers/*.json`.
- Vault-совместимость с исходным ProjectStore сохраняется (ADR-0004): служебные имена внутри
  vault не переименовывать.
- Сохранять пользовательские незакоммиченные изменения и отделять их от собственных.
